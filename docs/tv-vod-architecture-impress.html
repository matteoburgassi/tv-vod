TV App Architecture — Options

Three drivers shape the decision

Samsung (Tizen) and LG (webOS) don't support native Android/iOS SDKs — we need a different approach.

1

Maximise market coverage

Ship on Android/Google TV, Tizen (Samsung), webOS (LG), Apple TV — together >60 % of global Smart TV shipments.

2

Web-based DRM SDK

Playback relies on @digitalvirgo/drm-player — a façade built ad-hoc to wrap the licensed DRM SDK into a simple, reusable component for Bolt.new. Runs in a browser / WebView; non-web runtimes are ruled out.

matteoburgassi/drm-player
3

Bolt.new as accelerator

AI-powered rapid prototyping that excels at React/Vite web apps and React Native — making web architectures significantly faster to iterate on.

Architecture Comparison

Five approaches evaluated against our constraints

ApproachDescriptionProsCons
Fully Native One native app per OS (Swift / Kotlin / C++) Best performance & platform APIs N codebases, N teams; N DRM SDK integrations (one per platform); no Bolt.new leverage ✓
Cross-platform Native Single codebase → native (React Native, Flutter) Shared logic, native rendering; Bolt.new can scaffold RN No Tizen / webOS → misses ~25 % market; DRM SDK needs a WebView ✘
Lightning / WPE TV-specific JS framework (Metrological) Built for low-end SoCs, operator ecosystem Vendor lock-in; DRM integration not guaranteed; no Bolt.new support ✘
Packaged Web App Bundled HTML/JS/CSS inside each shell Offline-capable, store-distributed; Bolt.new can generate it DRM licence requires hosted origin; re-packaging on every update ✘
Hosted Web App (Hybrid) Thin native shell loads a remote SPA in a WebView Single codebase, OTA updates, DRM ✓, all target OSes; Bolt.new ideal for React/Vite iteration Needs connectivity; WebView perf varies by device ✓

Server API Layer

Cloudflare Worker — CORS proxy + device-code authentication

  • Cloudflare Worker (proxy/src/index.ts) deployed at smartvideo-cors-proxy.*.workers.dev.
  • CORS reverse proxy — SPA runs on a different origin; Worker forwards & injects CORS headers:
    /smartvideo/* → SmartVideo API
    /auth/* → DVE User API
  • Dev proxy — Vite mirrors the same paths locally.
  • Client package — tv-vod-auth/deviceCode.ts wraps the three device endpoints.

Device-code (QR) auth flow

  1. TV calls POST /device/code → Worker generates 6-char PIN, stores { status: 'pending' } in KV.
  2. TV displays QR code encoding the pairing URL with the PIN.
  3. User scans QR → PairPage lets them log in → POST /device/verify.
  4. TV polls GET /device/poll every 3 s → once complete, Worker returns user.
